==================================================

4. Execute that backlog using subagents wherever parallelization is useful.

6. Do not stop until the MVP Definition of Done is satisfied, except for true external blockers such as unavailable credentials or services.

==================================================
PHASE 1 — PRD ANALYSIS
==================================================

Read the complete PRD.

Build a requirements matrix containing:

- Requirement ID
- PRD requirement
- MVP priority
- Current implementation status
- Files/components likely involved
- Dependencies
- Acceptance criteria
- Verification method

Classify requirements:

P0 = required for MVP to function
P1 = important for MVP but not foundational
P2 = desirable but can wait
P3 = explicitly post-MVP

Do not silently expand scope.

If the PRD contains ambiguity:
choose the simplest reasonable implementation that satisfies the apparent MVP intent and record the assumption.

Favor shipping the MVP over speculative architecture.

==================================================
PHASE 5 — SUBAGENT EXECUTION
==================================================

For each wave:

1. Identify independent tasks.

2. Spawn appropriate subagents.

3. Give each agent:
   - exact task
   - relevant PRD section
   - acceptance criteria
   - allowed/expected files
   - dependencies
   - required tests
   - instruction to inspect existing code before modifying it
   - instruction to avoid unrelated refactoring

4. Where isolation/worktrees are available, use them for parallel work.

5. Avoid assigning multiple agents concurrent ownership of the same files unless absolutely necessary.

6. Require every implementation agent to:
   - implement the feature
   - run relevant tests
   - run type/lint checks where appropriate
   - inspect its diff
   - report exactly what changed
   - report tests executed
   - report remaining concerns

The orchestrator should continue coordinating other independent work while subagents execute.

==================================================
CHECKPOINT POLICY
==================================================

At the end of every wave:

1. Integrate completed work.
2. Resolve merge conflicts carefully.
3. Run appropriate validation.
4. Verify the application still builds.
5. Run relevant automated tests.
6. Update docs/progress.md.
7. Update docs/execution-plan.md if reality differs from the original plan.
8. Inspect git diff/status.
9. Create a descriptive git checkpoint commit if repository policy permits.

Use checkpoint messages similar to:

checkpoint: foundation complete
checkpoint: authentication workflow complete
checkpoint: core MVP workflows complete
checkpoint: integration tests passing

Never commit secrets, credentials, generated junk, or temporary diagnostic files.

==================================================
FAILURE / RETRY LOOP
==================================================

When implementation or tests fail:

Do not immediately escalate everything to the most expensive model.

Use this escalation sequence:

1. Let the original implementation agent diagnose/fix.
2. If unresolved, use a fresh Terra review/debug agent.
3. If still unresolved and genuinely complex, escalate to Sol.

For difficult failures:

REPRODUCE
→ isolate
→ identify root cause
→ implement minimal fix
→ regression test
→ integrate
→ continue

Do not repeatedly apply speculative changes without reproducing the problem.

Limit repeated unsuccessful approaches.
After 2-3 failed approaches, reconsider the underlying assumption or architecture.

==================================================
FINAL MVP REVIEW
==================================================

When all planned P0/P1 work appears complete, DO NOT immediately stop.

Spawn independent review tasks where useful:

REVIEW AGENT 1 — PRD compliance
Compare implementation against every MVP requirement.

REVIEW AGENT 2 — code quality
Look for obvious defects, dead paths, race conditions, incorrect assumptions, and maintainability problems.

REVIEW AGENT 3 — security
Check authentication, authorization, validation, secrets, unsafe data exposure, and common application vulnerabilities.

REVIEW AGENT 4 — test/UX
Attempt critical workflows and identify missing states or broken integration.

Use Terra for these reviews unless complexity requires Sol.

Aggregate findings.

Classify findings:

BLOCKER
HIGH
MEDIUM
LOW

Fix BLOCKER and HIGH findings before declaring MVP complete.

Fix MEDIUM findings when inexpensive and clearly beneficial.

Record LOW/post-MVP issues without allowing them to derail completion.
