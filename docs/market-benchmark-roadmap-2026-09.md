# PATH market benchmark and product roadmap

**Reviewed:** September 23, 2026. **Repository:** `grandpajoe1980/permit_tracker`, `main` at `712c010e13d02e38078fe4530d037ce9a1dde964`.
**Scope:** Source and migration review, existing PRD and backlog, focused local checks, and public product documentation. No authenticated production walkthrough or independent vendor trial was performed.

## Recommendation

**Use Accela Civic Platform with ePermitHub Digital Plan Room as the primary feature benchmark for government permitting.** It covers configurable workflows, public intake, plan review, GIS, field inspections, communications, reporting, and connections to other systems. Accela's pre-application guidance and document review are particularly useful references for PATH. This is a product judgment based on the requirements here and published capabilities, not a verified claim of market share or universal superiority.

**Keep PATH's distinctive purpose:** one project delivery view across state agencies, local governments, federal authorities, and the private applicant. Formal regulatory records should remain with each authority until that authority expressly makes PATH its system of record. For a very large industrial project, benchmark PATH's project controls against Oracle Primavera Cloud and its controlled document exchange against Oracle Aconex. Evaluate ServiceNow Public Sector Digital Services and its License and Permit Playbook before building a full government case-management suite from scratch; the organization already uses ServiceNow, but existing ITSM/ITOM licenses do not establish access to that separate product.

| Product | Strongest relevant capability | Limit for this use case |
| --- | --- | --- |
| **Accela Civic Platform + ePermitHub** | Full agency permitting lifecycle, configurable agency records, electronic plan review and applicant portal | An agency platform is not automatically a consolidated control room for independently governed federal, state, parish, utility, and applicant schedules. |
| **OpenGov Permitting & Licensing** | Approachable public portal, configurable multi-department workflow, fees and GIS visibility | Its published positioning centers on local community development. |
| **Clariti Enterprise** | Configurable high-volume city/county permitting, concurrent reviews, Salesforce foundation | Its published positioning centers on large cities and counties. |
| **Tyler Enterprise Permitting & Licensing** | Mature city/county permitting, eReviews, payments, field inspections | Its published positioning centers on city and county regulatory operations. |
| **ServiceNow Public Sector Digital Services** | Government cases, assignment, playbooks, service requests, license and permit workflows | Validate license, configuration effort, agency adoption, plan review, and cross-jurisdiction governance before selecting it as PATH's core. |
| **Oracle Primavera Cloud / Aconex** | Major-project schedule, risk, document control, correspondence across organizations | They are project delivery systems; a statutory permit decision stays with the relevant agency. |

## What the current repository actually provides

PATH has meaningful foundations: authenticated customer and staff views; customer intake with confirmation, drafts, and triage; assignment groups; workstreams and versioned workflows; RFIs and coordination requests; audit and in-app notification records; an authorization catalog with source/provenance labels; private versioned documents; a Gantt with task dependencies; a role-aware admin explorer. The production data design uses Supabase PostgreSQL, Storage, and RLS. See `lib/repository.ts`, `lib/supabase/`, `components/path/`, `components/cockpits/`, and `supabase/migrations/`.

The following observations limit claims of parity:

| Finding | Source evidence | Consequence |
| --- | --- | --- |
| The operational shell is still centered on one demo project. | `lib/repository.ts` defaults hydration to `PRJ-PECAN-2026`; `app/page.tsx` hydrates that default and holds the selected project in a singleton repository; `app/projects/[projectNumber]/page.tsx` validates a route and redirects to the shared project shell. | Multiple independent projects and customers need project selection and route-scoped state before this can be a platform. |
| PATH tracks an **external** permit filing and its manually recorded status; formal filing remains with the issuing agency. | `docs/PRD.MD` §3 and CP-04; `db/schema.ts` `externalFilings`; `components/cockpits/PermitCatalogPanel.tsx`. | Separate PATH status, external agency status, source, freshness, and evidence on every screen. Agency synchronization requires authorized integration. |
| Core agency transactions are absent from the current app's production model. | No substantive parcel/GIS, fee/payment, inspection scheduling/result, issuance, or renewal module in `app/`, `lib/supabase/`, and migrations; `inspection` appears as a task type. `docs/PRD.MD` §3 explicitly excludes payments initially. | No Accela-level full permit lifecycle yet. This is a planned expansion, not a defect against the current MVP scope. |
| Plan review manages files and decisions, but lacks a coordinated sheet markup and comment-resolution workspace. | `components/cockpits/DocumentVaultPanel.tsx`, `components/documents/DocumentViewerModal.tsx`, `lib/supabase/storage.ts`; compare Accela's ePermitHub revision and markup process. | Reviewers and applicants cannot work through plan sheets and correction cycles like an electronic plan room. |
| A reachable schedule simulator falsely reports promotion. | `components/cockpits/WorkstreamGraphGantt.tsx` renders `InteractiveScheduleSimulator`; its `handlePromoteScenario` in `components/cockpits/InteractiveScheduleSimulator.tsx` only sets a success message, without a server mutation. The simulator reads a fixture through `getFullProjectRecord()`. | Label it a simulation and remove/disable promotion until a permissioned, persisted forecast approval exists. |
| The daily escalation scan is not a durable scheduled service. | `lib/engines/sla-worker.ts` mutates the in-memory repository and notifications; `components/cockpits/DailyCommandCenter.tsx` invokes it locally and is not part of the operational shell. | Move deadline evaluation, idempotent events, and delivery monitoring into a server job before claiming automatic escalation. |
| Public-comment demo code is unsafe to expose. | `components/cockpits/PublicTransparencyPortal.tsx` displays “Comment Successfully Filed” after a local state update, without a network or database write; the component is not wired into `app/page.tsx`. | Keep it out of published routes. The PRD requires authoritative external comment links, not PATH acceptance of comments. |
| The current quality gate does not prove a connected release. | At this SHA, `npx tsc --noEmit` has eight errors in `TicketWorkflowEditor.tsx`, `operational-ux.ts`, and `repository.ts`. A focused 18-test Node subset passes; `docs/next-development-review.md` records earlier credential-skipped and unverified browser journeys. | Fix typing and rerun authenticated multi-persona, storage, RLS, and browser tests before treating prior `[x]` PRD marks as verified. |
| Large coupled modules slow expansion. | `app/page.tsx` is 2,783 lines; `lib/repository.ts` is 3,134 lines. Supabase migrations are canonical, while `db/schema.ts` is documented legacy SQLite metadata (`docs/architecture.md`). | Extract by domain and use forward migrations; avoid treating the legacy Drizzle schema as the PostgreSQL source of truth. |

**Status convention for the roadmap:** `implemented in code`, `verified with local behavior`, `verified with authenticated browser and database`, or `not implemented`. A checked box in `docs/PRD.MD` is not a substitute for acceptance evidence.

## Feature parity target

To match a leading **agency permitting product**, PATH eventually needs: guided eligibility and forms; trusted applicant identity; configurable rules, routing, completeness and concurrent review; document plan-room correction cycles; statutory clock and notice workflows; fee assessment and payments; parcel/GIS context; inspection scheduling and results; signed issuance with conditions; amendment, appeal, renewal and closure; applicant communications; scoped analytics, audit and retention; resilient integration and operational support. Some jurisdictions may keep payments, inspections, and final issuance in their own systems: PATH can show synchronized evidence and links while those records remain authoritative there.

To match **major-project coordination**, PATH needs a real multi-project portfolio, cross-agency dependency graph, approved schedule baselines and change history, accountable commitments and decision logs, risks and mitigations, disciplined drawing transmittals, resource capacity, external milestone reconciliation, and audience-specific executive and applicant views. Integrating a specialist scheduler is likely better than rebuilding all of Primavera.

## Dependency-aware delivery roadmap

Effort bands assume a small dedicated product team (product owner, designer, 2–4 engineers, quality engineer, agency process SMEs), plus agency participation. They are planning ranges, not commitments. Phases can overlap after their prerequisites and acceptance gates are met.

| Phase | Priority and range | Concrete deliverables | Exit evidence |
| --- | --- | --- | --- |
| **0. Establish a trustworthy baseline** | P0, 2–4 weeks | Fix eight TypeScript errors; record build and migration state; reconcile `docs/PRD.MD` checkboxes against tested behavior; disable false schedule promotion; keep dormant public-comment UI unexposed; finish existing S4–S7 navigation, cross-person RFI/document/coordination, authorization, and catalog verification. Add CI gates for type, build, focused behavior and required connected tests. | An applicant and two agencies complete submit → triage → RFI/document revision → determination through fresh browser sessions; database and Storage read-back, audit/notifications, negative RLS checks; no silent credential skips in the release gate. |

### First buildable backlog, in order

1. **PATH-001 — Honest release gate:** repair type errors, run build, and make connected tests fail clearly without required secrets; capture exact baseline and deployment SHA.
2. **PATH-002 — Truthful user actions:** replace the simulator's false “promoted” success with an explicit unsaved scenario; remove any possibility of routing the local-only comment form; audit other success toasts for committed writes.
3. **PATH-003 — One verified cross-person journey:** close the existing S4/S5 acceptance gaps with customer, reviewer, receiving agency, fresh sessions, real non-empty file, failed write and unauthorized access; record database/audit/notification evidence.
4. **PATH-004 — Project scope contract:** replace the default demo project in hydration, URLs, queries and mutation calls with an explicit authorized project context; prove tenant isolation in a two-project fixture.
5. **PATH-005 — Authority and provenance:** place PATH workflow status next to external filing status with its agency, record ID, last verification, receipt and confidence; add a reconciliation queue before any external feed.
6. **PATH-006 — Pilot workflow design:** have two agencies validate actual triggers, required forms, notices, clock policy, decision roles and customer-safe wording; implement configuration rather than another hardcoded SpaceX flow.
7. **PATH-007 — Vendor and integration decision:** scripted comparison of Accela, ServiceNow PSDS, and one willing agency's incumbent; test both a permitting case and a multi-agency schedule handoff. Document buy, integrate, and build ownership before expanding the schema.

### Product decisions needed before phases 2–5

- Which two agencies and permit types will be the initial real pilot, and who legally issues each decision?
- Will PATH be an agency system of record for any permit type, or only the statewide project coordination and customer view?
- Which agency systems expose supported APIs and allow data sharing? Who certifies an external status and corrects conflicts?
- Does the organization have or want ServiceNow PSDS licensing, and should cases be handled there while PATH owns the cross-agency project view?
- Will plan review and the detailed master schedule be built inside PATH or supplied by ePermitHub/Aconex/Primavera integrations?

**Practical goal:** a credible two-agency coordination pilot after phases 0–1 and part of 3; comprehensive Accela-like agency transaction parity is a separate multi-agency program measured in many months, contingent on authority, funding, integrations, and process ownership.
